Keycloak TLS + mTLS
+ Postgres Stack

Self-contained Keycloak 26.6.1 deployment with inbound server TLS, mutual TLS client authentication, custom internal CA trust for outbound HTTPS, and a Postgres 17 backend — running locally via Docker/Podman Compose or on OpenShift with passthrough Routes.

keycloak 26.6.1 postgres 17 docker / podman compose openshift passthrough tls mtls client auth custom internal ca multi-domain issuer
§ 01 — The Problem

Before vs. After

✕ Before — HTTP only, no trust controls
1
Client connects to Keycloak over plain HTTP — credentials and tokens travel unencrypted.
↓
2
No client cert validation: any caller can hit the token endpoint. API clients are authenticated only by client secret.
↓
3
Keycloak cannot call internal services signed by a company/internal CA — TLS handshakes fail with certificate errors.
↓
4
OpenShift deployment requires re-encryption or edge termination — Keycloak never sees the original TLS connection.
✓ After — Full TLS stack, zero custom images
1
Keycloak serves HTTPS on :8443 with its own server cert/key mounted — no sidecar, no custom image.
↓
2
mTLS client auth via KC_HTTPS_CLIENT_AUTH=request|required: API clients must present a cert trusted by the client truststore.
↓
3
Internal CA certs dropped into certs/internal-ca/ and mounted via KC_TRUSTSTORE_PATHS — Keycloak trusts them for all outbound calls.
↓
4
OpenShift passthrough Route forwards raw TCP to Keycloak :8443 — Keycloak terminates TLS itself, preserving client certs end-to-end.

§ 03 — Trust Directions

Three Independent TLS Trust Planes

Inbound — Serve HTTPS
Server Certificate
Keycloak presents its own server TLS cert to connecting clients. The cert must match all served hostnames in its SAN.

KC_HTTPS_CERTIFICATE_FILE
KC_HTTPS_CERTIFICATE_KEY_FILE

Mounted at:
/opt/keycloak/conf/tls/tls.crt
/opt/keycloak/conf/tls/tls.key
Inbound — Verify Client Certs (mTLS)
Client Truststore
Keycloak optionally or mandatorily requests a client certificate and verifies it against the PKCS12 truststore.

KC_HTTPS_CLIENT_AUTH=request|required
KC_HTTPS_TRUST_STORE_FILE
KC_HTTPS_TRUST_STORE_PASSWORD

Mounted at:
/opt/keycloak/conf/mtls/client-truststore.p12
Outbound — Trust Internal CA
Internal CA Truststore
Keycloak makes outbound HTTPS calls (e.g. to identity providers, LDAP over TLS, webhooks). Custom/internal CA certs are added to Keycloak's trust without rebuilding the image.

KC_TRUSTSTORE_PATHS

Mounted at:
/opt/keycloak/conf/truststores/internal-ca

Drop any .crt / .pem file into certs/internal-ca/.

Dev Cert Generation
# generate all certs for local dev
# 1. Server cert — localhost SAN openssl req -x509 -newkey rsa:4096 \ -nodes -days 365 \ -keyout certs/server/tls.key \ -out certs/server/tls.crt \ -subj "/CN=localhost" \ -addext "subjectAltName=\ DNS:localhost,IP:127.0.0.1" # 2. Client CA openssl req -x509 -newkey rsa:4096 \ -nodes -days 365 \ -keyout certs/client-ca/client-ca.key \ -out certs/client-ca/client-ca.crt \ -subj "/CN=kc-playground-client-ca" # 3. PKCS12 truststore for Keycloak keytool -importcert -noprompt \ -alias client-ca \ -file certs/client-ca/client-ca.crt \ -keystore certs/client-ca/client-truststore.p12 \ -storetype PKCS12 \ -storepass changeit
§ 06 — Deployment Modes

Running the Stack

Mode Command Key differences
dev docker compose up start-dev: no build step, embedded H2 cache disabled, hot reload. Postgres is still used as backend DB.
production KEYCLOAK_START_COMMAND=start KC_HOSTNAME=localhost docker compose up start: runs build optimisation, enables distributed caches. Fixed KC_HOSTNAME required in single-domain mode.
production multi-domain KEYCLOAK_START_COMMAND=start KC_HOSTNAME_STRICT=false docker compose up Dynamic issuer per domain. Do not set KC_HOSTNAME. Issuer is derived from the incoming Host header.
hard mTLS KC_HTTPS_CLIENT_AUTH=required docker compose up Every caller must present a client cert trusted by client-truststore.p12. Admin UI and browser access break without a valid cert.
OpenShift Apply Route + Service manifests, mount keycloak-tls Secret Passthrough Route on each domain (dhohner.de / .at / .intern). All routes point to same Service :8443. Keycloak terminates TLS.
reset DB docker compose down -v Removes postgres-data named volume. All realms, users, and sessions are lost.

Service Probe Interval / Retries Notes

§ 09 — Edge Cases

Scenarios & Expected Behaviour

Scenario Expected behaviour Severity
KC_HTTPS_CLIENT_AUTH=required + browser access Browser has no client cert → TLS handshake fails immediately. Admin UI and OIDC browser flows stop working. Use required only on dedicated API-only Routes where every caller can supply a cert. breaking
Fixed KC_HOSTNAME set in multi-domain mode Keycloak hardcodes the issuer URL. Token issuer for dhohner.at still reads dhohner.de → OIDC validation fails. Remove KC_HOSTNAME and keep KC_HOSTNAME_STRICT=false. breaking
Missing SAN on server cert (passthrough TLS) Clients connecting to dhohner.at receive a cert that doesn't cover that hostname → browser shows certificate error. The cert's SAN must include all served domains. breaking
certs/internal-ca/ directory is empty Keycloak starts fine but won't trust any internal CA. Outbound HTTPS calls to services signed by the internal CA fail with SSLHandshakeException. Drop the CA certs and restart. runtime error
client-truststore.p12 missing at startup Keycloak fails to start when KC_HTTPS_CLIENT_AUTH is set and the truststore file doesn't exist or can't be read. Ensure the file exists and has correct permissions before compose up. startup failure
mTLS client cert from wrong CA Cert presented but its issuer isn't in client-truststore.p12 → TLS handshake fails with unknown ca. Import the correct client CA into the truststore and restart. auth failure
KC_PROXY_HEADERS not set behind a proxy Keycloak uses the raw container IP for redirect URIs and issuer. Auth redirects break. Always set KC_PROXY_HEADERS=xforwarded when behind OpenShift router or any reverse proxy. runtime error
Postgres healthcheck slow on first boot Keycloak has a start_period: 30s before retries count. On slow machines, increase start_period or retries to avoid premature failure. config
Server private key passphrase protected Keycloak cannot read passphrase-protected private keys at startup. Generate the key without a passphrase (-nodes flag in openssl). startup failure
§ 10 — Implementation Notes

Critical Considerations

No custom image required. All CA and certificate handling is achieved purely through volume mounts and environment variables on the official quay.io/keycloak/keycloak:26.6.1 image. KC_TRUSTSTORE_PATHS supports entire directories — drop files in, restart, done.
Management port :9000 is always plain HTTP. The health endpoint GET http://127.0.0.1:9000/health/ready does not use TLS even when HTTPS is enabled on :8443. The compose healthcheck uses /dev/tcp directly — no curl binary needed inside the container.
mTLS=required breaks all non-cert callers. Use KC_HTTPS_CLIENT_AUTH=request during development so browser-based admin and OIDC flows still work. Only switch to required on a separate Route/ingress path where all clients can supply a certificate.
OIDC multi-domain issuer constraint. When KC_HOSTNAME_STRICT=false and no fixed KC_HOSTNAME is set, Keycloak derives the issuer from the incoming Host header. OIDC clients must use discovery, authorization, token, and issuer validation for the exact same domain they entered through — cross-domain token reuse will fail issuer validation.
Truststore password in environment. KC_HTTPS_TRUST_STORE_PASSWORD and POSTGRES_PASSWORD are set as environment variables — acceptable for a local playground. In production, use Kubernetes Secrets or a secrets manager (Vault, AWS Secrets Manager, etc.) and never commit .env files containing real passwords.
start-dev vs start. start-dev skips the build/optimisation phase — it's fast for iteration but is not production-hardened. Switch to KEYCLOAK_START_COMMAND=start plus KC_HOSTNAME (or KC_HOSTNAME_STRICT=false) before any real deployment. Postgres is used in both modes.
